# 🛒 Aldi Budget Meal Planner

An AI-powered meal planning web app that builds a real shopping basket from the live Aldi Süd catalogue, then generates a personalised meal plan using Google Gemini — with verified budget maths and real nutrition data from the USDA FoodData Central database.

## How It Was Built

The project started from a simple question: *can an AI plan a week of meals that actually fit a real supermarket budget?*

### Stage 1 — Scraping the Catalogue
A Playwright-based scraper (`scraper.py`) navigates the entire Aldi Süd website, visiting every category and subcategory. It extracts product name, brand, price, and weight for each item, then deduplicates and saves everything to `aldi_catalog.json`. The scraper handles cookie banners, pagination, and unit parsing (grams, kg, ml, litres).

### Stage 2 — Basket Builder
Rather than dumping 1,000+ products into the AI prompt (which would be expensive and unreliable), a greedy basket builder (`/build-basket` endpoint) pre-selects the best-value products. It picks the cheapest item per subcategory until the budget would be exceeded, ensuring variety and guaranteed budget compliance before the AI is even involved.

### Stage 3 — AI Meal Planning
The filtered basket is sent to Google Gemini with a structured prompt (`ai_planner.py`). The prompt enforces a strict JSON schema, pro-rated costing rules, and cuisine/diet constraints. Gemini returns a full multi-day meal plan with ingredients, quantities, cooking instructions, and nutrition estimates.

### Stage 4 — Budget Verification
Python re-calculates every cost figure independently from the AI's response — ingredient by ingredient, meal by meal, day by day. Any discrepancy is flagged and the correct number overwrites the AI's claim. This catches hallucinated totals and ensures the plan never silently exceeds the budget.

### Stage 5 — Real Nutrition
Gemini's nutrition estimates are replaced with real USDA FoodData Central data. Each product title is translated from German, simplified, and looked up against the USDA API. Results are cached on disk. Dry-weight entries (rice, pasta, legumes) are adjusted to cooked-weight equivalents. A full calorie/protein/carbs/fat breakdown per serving is calculated from actual ingredient quantities.

### Frontend
A React + Vite + Tailwind CSS frontend guides the user through a two-step flow: review the shopping basket first, then generate the meal plan. A dashboard shows budget utilisation, BMI, TDEE, and daily nutrition bars. Each meal card opens a modal with ingredients, step-by-step instructions, and a nutrition tab.

## Features

- **Live Aldi catalogue** — scraped with Playwright, covers all food categories
- **Two-step flow** — review your basket before committing to meal generation
- **Budget enforcement** — greedy basket builder + Python re-verification of every cost figure
- **Multi-diet support** — omnivore, vegetarian, vegan (subcategory exclusions)
- **Cuisine selection** — 40+ cuisines from Italian to Ethiopian to Taiwanese
- **Body metrics** — Mifflin-St Jeor TDEE and protein targets (1.6 g/kg) with BMI display
- **Real nutrition data** — USDA FoodData Central replaces AI-estimated values
- **Cooked weight adjustment** — pasta, rice, legumes are adjusted from dry to cooked basis
- **Nutrition bars** — daily calories and protein tracked against TDEE/protein targets
- **Meal modal** — ingredients list, step-by-step instructions, per-serving and total nutrition
- **Retry logic** — Gemini API retries with exponential backoff on 503/429
- **Truncation recovery** — robust JSON parser recovers valid meal plans from truncated responses
- **Nutrition cache** — USDA lookups cached on disk, instant on subsequent runs
- **Plan days 1–7** — batch generation for longer plans to stay within model output limits

## Local Setup

### 1. Clone the repository

```bash
git clone <your-repo-url>
cd FB
```

### 2. Create and activate a Python virtual environment

```bash
python -m venv .venv

# Windows
.venv\Scripts\activate

# macOS / Linux
source .venv/bin/activate
```

### 3. Install Python dependencies

```bash
pip install fastapi uvicorn "google-genai" python-dotenv requests
```

For scraping (optional — a pre-scraped catalogue is included):

```bash
pip install playwright beautifulsoup4
playwright install chromium
```

### 4. Install frontend dependencies

```bash
cd frontend
npm install
cd ..
```

### 5. Set up environment variables

Create a `.env` file in the project root:

```env
GEMINI_API_KEY=your_gemini_key_here
USDA_API_KEY=your_usda_key_here
```

> The app works without `USDA_API_KEY` but nutrition values will fall back to AI estimates.

## Running the App

You need two terminals running simultaneously.

**Terminal 1 — Backend:**

```bash
# From the project root (FB/)
python -m uvicorn server:app --host 0.0.0.0 --port 8000 --reload
```

**Terminal 2 — Frontend:**

```bash
# From the frontend/ directory
cd frontend
npm run dev
```

Then open **http://localhost:5173** in your browser.

### Optional: Re-scrape the Aldi catalogue

```bash
python scraper.py
```

This takes 10–30 minutes and overwrites `aldi_catalog.json`. Only needed when prices change or you want fresh data.

### Optional: CLI usage

```bash
# Show / edit your profile
python main.py setup
python main.py profile

# Record spending
python main.py spend 12.50

# Generate a plan from the command line
python main.py ai-plan --days 3
python main.py ai-plan --dry-run   # preview prompt without calling the API
```

## Deploy to Render

The project ships with a `render.yaml` that declares both services. Render reads this file automatically when you connect the repo.

### Services

| Service | Type | Name |
|---|---|---|
| FastAPI backend | Web Service (Python) | `aldi-meal-planner-api` |
| React frontend | Static Site | `aldi-meal-planner` |

### Steps

**1. Push the repo to GitHub** (already done if you cloned this).

**2. Create a new Render Blueprint**
- Go to [dashboard.render.com](https://dashboard.render.com) → **New → Blueprint**
- Connect your GitHub repo
- Render detects `render.yaml` and creates both services automatically

**3. Set environment variables**

After the Blueprint is created, set these in the Render dashboard for each service.

For the **backend** (`aldi-meal-planner-api`):

| Variable | Value |
|---|---|
| `GEMINI_API_KEY` | Your Google Gemini API key |
| `USDA_API_KEY` | Your USDA FoodData Central key |
| `ALLOWED_ORIGINS` | Your frontend URL, e.g. `https://aldi-meal-planner.onrender.com` |

For the **frontend** (`aldi-meal-planner`):

| Variable | Value |
|---|---|
| `VITE_API_URL` | Your backend URL, e.g. `https://aldi-meal-planner-api.onrender.com` |

> **Order matters:** deploy the backend first to get its URL, then set `VITE_API_URL` on the frontend and trigger a redeploy.

**4. Trigger deploys**
- Backend: deploys automatically on push to `main`
- Frontend: rebuild triggered by push or manually from the dashboard

### Free tier notes

- Render free web services **spin down after 15 minutes of inactivity**. The first request after a cold start takes ~30 seconds. Upgrade to the Starter plan ($7/month) to avoid spin-down.
- The static site never spins down — it is served from Render's CDN.
- The USDA nutrition cache (`nutrition_cache.json`) is stored on the local filesystem and is **lost on every redeploy** on the free tier (ephemeral filesystem). Consider using a persistent disk ($1/month) or an external KV store if you want the cache to survive deploys.

## How Each Component Works

### `scraper.py`
Launches a headless Chromium browser, accepts the cookie banner once, then iterates through every category/subcategory URL in the `CATEGORIES` dict. For each page it waits for `div.product-tile` elements, parses brand, name, price, and weight using BeautifulSoup, and handles all unit formats (g, kg, ml, L). Deduplicates by URL keeping the most specific subcategory entry.

### `ai_planner.py`
**Stage 1 — `filter_catalog()`:** Loads the catalogue, keeps food-only categories, applies diet exclusions, sorts by price-per-kg, keeps the 3 cheapest items per subcategory, caps at 120 items, and enriches with USDA nutrition data in a background thread.

**Stage 2 — `build_prompt()`:** Constructs a detailed prompt with constraints (budget, diet, servings, cuisine), the numbered ingredient list with prices, and a strict JSON output schema. Includes TDEE/protein targets when body metrics are available.

**Stage 3 — `call_gemini()`:** Sends the prompt to the Gemini API with temperature 0.4 and up to 16,384 output tokens. Retries up to 4 times with exponential backoff on 503/429 errors.

**Stage 4 — `verify_budget()`:** Re-calculates costs from ingredient level up. Overwrites any AI-claimed total that differs from Python's arithmetic by more than €0.02. Flags budget overruns.

**Stage 5 — `compute_real_nutrition()`:** Builds a title→CatalogItem map. For each meal, looks up every ingredient's USDA data and calculates per-serving nutrition from `qty_used_kg`. Only overwrites a meal if all its ingredients resolved — never partial. Recomputes `day_nutrition` totals on a per-person basis.

### `nutrition.py`
Translates German product titles to English search queries using a compound-word-aware dictionary. Fetches from USDA FoodData Central, sorts results by data type (Foundation > SR Legacy > Survey > Branded) and word overlap. Applies sanity checks (calories 5–900 kcal/100g, protein checks for eggs/meat). Adjusts dry-weight values for pasta, rice, and legumes to cooked-weight equivalents. Caches all results on disk.

### `server.py`
FastAPI app with two POST endpoints. `/build-basket` runs the greedy budget-constrained basket builder. `/generate-plan` calls the full AI pipeline and appends computed user metrics (BMI, TDEE, daily protein) to the response. Both blocking operations run in a thread pool via `run_in_threadpool` so the async event loop is never blocked.

### Frontend (`App.jsx`)
State machine with stages: `idle → basket_loading → basket_review → loading → done | error`. Uses a `useRef` to store form values synchronously, avoiding React's async state update race condition when passing config from the basket step to the generation step.

## Pros & Cons

### Pros

- **Real prices, real products** — not hypothetical meals. Every ingredient costs what it actually costs at Aldi today.
- **Budget guaranteed** — two-stage enforcement (greedy builder + Python re-verification) means the plan can never silently exceed your budget.
- **Real nutrition, not hallucinations** — USDA data with cooked-weight adjustments gives accurate calorie and macro counts rather than AI guesses.
- **Two-step transparency** — you see and approve your shopping basket before the AI starts planning. No surprises.
- **Personalised targets** — Mifflin-St Jeor TDEE calculation and 1.6 g/kg protein target based on your actual body metrics.
- **40+ cuisines** — you can request Japanese, Ethiopian, Peruvian, or any combination; the AI adapts the recipes to the available ingredients.
- **Graceful degradation** — USDA lookup failures fall back to AI estimates silently. API rate limits, network errors, and truncated model responses are all handled without crashing.
- **Disk-cached nutrition** — after the first run, nutrition lookups are instant from cache.

### Cons

- **Aldi Süd only** — the scraper is specific to aldi-sued.de. Different Aldi regions or other supermarkets require a new scraper.
- **Scraper fragility** — if Aldi changes their HTML structure (class names, CSS selectors), the scraper breaks until updated.
- **Static catalogue** — `aldi_catalog.json` goes stale as soon as prices change. You need to re-run the scraper periodically.
- **AI recipe quality varies** — Gemini sometimes produces unrealistic ingredient combinations or odd quantities, especially for exotic cuisines with limited matching ingredients.
- **USDA coverage gaps** — some German-specific products (Magerquark, certain Wurst varieties, specialty cheeses) don't have great USDA matches and fall back to hardcoded values or AI estimates.
- **Single-user** — the profile system is a local JSON file, not a database. Not suitable for multi-user deployment without changes.
- **Gemini rate limits** — the free tier limits concurrent requests. Heavy use may hit 429 errors, triggering retry delays.
- **No allergen tracking** — the system has no awareness of common allergens. Users with allergies must manually review plans.
- **Nutrition is approximate** — even with USDA data, quantities come from the AI's estimates of `qty_used_kg`. The actual nutrition depends on how closely the AI's quantities match what you'd really use.

## Known Limitations

- The nutrition background thread fetches up to 120 products on first run. With a personal USDA key this takes ~10 seconds and runs concurrently with the AI call (which takes longer), so the first generation after a cold cache may show AI-estimated nutrition for meals whose ingredients hadn't resolved yet. Subsequent runs are instant from cache.
- Gemini model name must match an available model on your API key's tier. If you get a 404 model error, update `MODEL_NAME` in `ai_planner.py`.
- The greedy basket builder does not guarantee the AI will use every item in the basket — it constrains the ingredient list, but the AI may choose not to use all of them.
